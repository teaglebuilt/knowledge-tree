# Alertmanager Deep Configuration

## Overview

Alertmanager is responsible for receiving, deduplicating, grouping, and routing alerts generated by Prometheus, and sending them to various notification channels. This document covers high-availability deployment, routing tree design, suppression/silence rules, and mainstream Receiver integration.

## 1. High-Availability Cluster Deployment

### 1.1 Gossip Cluster Architecture

## 2. Routing Tree Design

### 2.1 Multi-Level Routing Strategy

```yaml
route:
  # Default receiver
  receiver: slack-default
  # Default grouping
  group_by: ['alertname', 'namespace', 'severity']
  # Group wait time
  group_wait: 30s
  # Group interval
  group_interval: 5m
  # Repeat interval
  repeat_interval: 4h

  routes:
  # P0 critical alerts (immediate notification)
  - match:
      severity: critical
    receiver: pagerduty-critical
    group_wait: 10s
    group_interval: 1m
    repeat_interval: 15m
    continue: true

  # Production environment alerts
  - match_re:
      namespace: ^production$
    receiver: slack-production
    group_by: ['alertname', 'namespace', 'pod']
    routes:
    # API service alerts
    - match:
        app: api-gateway
      receiver: slack-api-team
      group_wait: 15s

    # Database alerts
    - match:
        app: postgresql
      receiver: slack-dba-team
      group_wait: 10s

    # Alert escalation (unresolved for 15 minutes)
    - match:
        severity: critical
      receiver: pagerduty-critical
      routes:
      - match:
          namespace: production
        receiver: phone-call
        group_wait: 5s
        repeat_interval: 5m

  # Non-production environment
  - match_re:
      namespace: ^(staging|development)$
    receiver: slack-staging
    group_wait: 5m
    repeat_interval: 12h

  # Watchdog (liveness probe)
  - match:
      alertname: Watchdog
    receiver: null
```

### 2.2 Inheritance and Overriding

```yaml
route:
  receiver: default-receiver
  group_by: ['alertname']
  group_wait: 30s
  group_interval: 5m
  repeat_interval: 4h

  routes:
  # Child routes inherit parent route's group_by, but can override
  - match:
      severity: critical
    receiver: critical-receiver
    # Override grouping strategy
    group_by: ['alertname', 'namespace', 'pod']
    # Override time parameters
    group_wait: 10s
    repeat_interval: 15m
    # Inherit parent route's match (default false)
    continue: false
```

## 3. Suppression Rules

### 3.1 Cascading Suppression

```yaml
inhibit_rules:
# Suppress all Pod alerts on a node when the node goes down
- source_match:
    alertname: NodeDown
    severity: critical
  target_match_re:
    alertname: .*
  equal: ['node']

# Suppress namespace-level alerts when cluster is unhealthy
- source_match:
    alertname: ClusterUnhealthy
    severity: critical
  target_match:
    severity: warning
  equal: ['cluster']

# Suppress performance alerts when critical service is down
- source_match:
    alertname: ServiceDown
    severity: critical
  target_match_re:
    alertname: (HighLatency|HighErrorRate)
  equal: ['namespace', 'service']

# Suppress P1/P2 alerts when P0 alert is firing
- source_match:
    severity: critical
  target_match:
    severity: warning
  equal: ['namespace', 'alertname']
```

### 3.2 Time Window Suppression

```yaml
inhibit_rules:
# Maintenance window suppression
- source_match:
    alertname: MaintenanceWindow
  target_match_re:
    alertname: .*
  equal: ['namespace']

# Suppression during deployments
- source_match:
    alertname: DeploymentInProgress
  target_match_re:
    alertname: (PodRestart|ContainerCrashLooping)
  equal: ['namespace', 'deployment']
```

    "endsAt": "2026-07-02T12:00:00Z",

### 4.2 Periodic Maintenance Silence

```yaml
# Periodic maintenance window (every Wednesday 22:00-23:00)
apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: maintenance-silence
  namespace: monitoring
spec:
  matchers:
  - name: namespace
    value: production
  inhibitRules:
  - sourceMatch:
    - name: alertname
      value: MaintenanceWindow
    targetMatch:
    - name: severity
      value: warning
```

## 5. Grouping Policies

### 5.1 Optimal Grouping Configuration

```yaml
route:
  # Basic grouping
  group_by: ['alertname', 'namespace']

  routes:
  # Fine-grained grouping by Pod (suitable for dense alerts)
  - match:
      app: api-gateway
    group_by: ['alertname', 'namespace', 'pod']

  # Grouping by cluster (suitable for multi-cluster alerts)
  - match:
      severity: critical
    group_by: ['alertname', 'cluster']

  # No grouping (suitable for low-frequency important alerts)
  - match:
      alertname: Watchdog
    group_by: [...]
```

### 5.2 Time Parameter Optimization

```yaml
route:
  # group_wait: How long to wait after receiving the first alert before sending (to aggregate same-group alerts)
  group_wait: 30s

  # group_interval: Interval for sending same-group alerts
  group_interval: 5m

  # repeat_interval: Repeat notification interval for unresolved alerts
  repeat_interval: 4h

  routes:
  # Critical alerts: shorten all times
  - match:
      severity: critical
    group_wait: 10s
    group_interval: 1m
    repeat_interval: 15m

  # Low-priority alerts: extend times
  - match:
      severity: info
    group_wait: 5m
    group_interval: 30m
    repeat_interval: 24h
```

## 6. Receiver Integration

### 6.1 Slack Integration

```yaml
receivers:
- name: slack-production
  slack_configs:
  - api_url: 'https://hooks.slack.com/services/T00/B00/xxx'
    channel: '#alerts-production'
    send_resolved: true
    title: |
      [{{ .Status | toUpper }}{{ if eq .Status "firing" }}:{{ .Alerts.Firing | len }}{{ end }}]
      {{ .CommonLabels.alertname }}
    text: |
      {{ range .Alerts }}
      *Alert:* {{ .Annotations.summary }} - `{{ .Labels.severity }}`
      *Description:* {{ .Annotations.description }}
      *Namespace:* {{ .Labels.namespace }}
      *Pod:* {{ .Labels.pod }}
      *Started:* {{ .StartsAt }}
      {{ if .EndsAt }}*Resolved:* {{ .EndsAt }}{{ end }}
      {{ end }}
    actions:
    - type: button
      text: 'View in Grafana :grafana:'
      url: '{{ (index .Alerts 0).GeneratorURL }}'
    - type: button
      text: 'Runbook :book:'
      url: '{{ (index .Alerts 0).Annotations.runbook_url }}'
```

### 6.2 PagerDuty Integration

```yaml
receivers:
- name: pagerduty-critical
  pagerduty_configs:
  - routing_key: '<pagerduty-integration-key>'
    severity: '{{ .GroupLabels.severity }}'
    description: |
      [{{ .Status | toUpper }}] {{ .CommonLabels.alertname }}
    details:
      firing: '{{ .Alerts.Firing | len }}'
      resolved: '{{ .Alerts.Resolved | len }}'
      namespace: '{{ .GroupLabels.namespace }}'
      cluster: '{{ .GroupLabels.cluster }}'
    source: '{{ .CommonLabels.source }}'
    component: '{{ .CommonLabels.component }}'
    group: '{{ .GroupLabels.namespace }}'
    class: '{{ .GroupLabels.alertname }}'
```

## 7. Best Practices

```
Alertmanager Configuration Checklist:

□ Deploy 3-replica high-availability cluster
□ Design clear routing tree (by severity → namespace → app)
□ Configure reasonable grouping strategy (avoid alert storms)
□ Configure suppression rules (cascading suppression)
□ Use silence rules for maintenance windows
□ Integrate multiple Receivers (Slack/PagerDuty/Email)
□ Configure alert escalation strategy
□ Regularly review routing rules
□ Test alert notification pipeline
□ Monitor Alertmanager's own health
```
